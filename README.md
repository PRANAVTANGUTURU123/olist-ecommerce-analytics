# Olist Brazilian E-Commerce — Data Analytics Portfolio Project

A full data-analyst portfolio project on the [Olist Brazilian E-Commerce
dataset](https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce) (~99k
orders, 2016–2018): Python data cleaning + EDA, a SQL analysis layer over a
star schema, a Power BI build spec, and a written business-insights report.

## What's here

| Path | Contents |
|---|---|
| `data/raw/` | The 9 original Kaggle CSVs (gitignored — see Setup) |
| `data/processed/` | Cleaned star-schema fact/dimension tables, CSV + Parquet (gitignored, regenerated by the pipeline) |
| `data/olist.duckdb` | The same star schema loaded into DuckDB (the SQL layer's database) |
| `notebooks/01_data_cleaning_eda.ipynb` | Data-quality profiling, cleaning decisions, orphan-key checks, exploratory charts |
| `scripts/01_clean_and_build_tables.py` | The production cleaning pipeline — reads `data/raw`, writes `data/processed` + `data/olist.duckdb` |
| `sql/*.sql` | Business-question queries organized by theme (sales, category, delivery, regional, payments, sellers, retention) |
| `sql/run_queries.py` | Runs every query in `/sql`, saves results to `sql/results/` |
| `dashboard/powerbi_spec.md` | Power BI data model, relationships, DAX measures, and a page-by-page visual layout plan |
| `report/insights_report.md` | ~1-page written findings + recommendations |

## Tech stack

- **Python** (pandas, matplotlib, seaborn) — cleaning + EDA
- **SQL via DuckDB** — the core analytical querying layer, run directly
  against the star-schema Parquet/CSV tables
- **Power BI Desktop** — final dashboard (built manually from the spec in
  `/dashboard`, not included in this repo)

## The data model

A star schema built from the 9 raw tables (full rationale in the notebook):

- **Facts:** `fact_order_items` (grain: order line item), `fact_payments`
  (grain: payment installment), `fact_reviews` (grain: review)
- **Dimensions:** `dim_orders` (grain: order — the shared bridge the other
  facts key off via `order_id`), `dim_customers`, `dim_sellers`,
  `dim_products`, `dim_date`, `dim_geolocation`

This is what makes Power BI import trivial — no need to re-join across all 9
raw files inside Power BI itself.

## Setup / how to reproduce

1. Download the dataset from
   [Kaggle](https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce) and
   place the 9 CSVs in `data/raw/`.
2. Install dependencies: `pip install -r requirements.txt`
3. Run the cleaning pipeline (writes `data/processed/*` and
   `data/olist.duckdb`):
   ```
   python scripts/01_clean_and_build_tables.py
   ```
4. Run the SQL business-question queries (writes `sql/results/*.csv`):
   ```
   python sql/run_queries.py
   ```
5. (Optional) Re-execute the EDA notebook:
   ```
   jupyter nbconvert --to notebook --execute --inplace notebooks/01_data_cleaning_eda.ipynb
   ```
6. Open Power BI Desktop, import from `data/processed/`, and follow
   `dashboard/powerbi_spec.md` to build the data model, DAX measures, and
   report pages.

## Key findings (full detail in `report/insights_report.md`)

- **Delivery delay is the strongest lever on customer satisfaction:** orders
  8+ days late average 1.73★ vs. 4.32★ for early deliveries — a 2.6-star
  swing. Lateness concentrates in a handful of northern/northeastern states
  (AL, MA, PI) at 2–4x the national rate.
- **~7% of scored seller revenue (R$778k) comes from sellers with either a
  sub-3.5 average review score or a 20%+ late rate** — a concrete
  seller-quality risk list.
- **Repeat purchases are rare (3.0% of customers) but valuable** (5.7% of
  revenue) — a real signal, but too thin in this 2-year snapshot to treat as
  a core retention KPI.
- **Installment count tracks basket size directly:** upfront credit-card
  payments average R$96; 13+-installment payments average R$410.

## Caveats

- `order_status` includes non-delivered states (canceled, processing,
  etc.); revenue metrics throughout exclude `canceled` and `unavailable`
  orders unless noted otherwise.
- `customer_id` is unique per order; `customer_unique_id` is the actual
  person and is what the retention analysis uses. The dataset is a fixed
  2016–2018 window, so "single order in-window" doesn't mean "single order
  ever" — treat retention findings as directional (see the report's caveat
  section).
- `dim_geolocation` is deduplicated from ~1M noisy raw pings down to one
  averaged lat/lng per zip-code prefix, with a handful of out-of-Brazil
  coordinates dropped as bad geocodes.
